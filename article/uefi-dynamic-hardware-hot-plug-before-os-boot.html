UEFI Dynamic Hardware Hot-Plug Before OS Boot

The Unified Extensible Firmware Interface (UEFI) handles dynamic hardware hot-plug events prior to operating system boot through a combination of periodic polling, timer events, and firmware bus drivers within a cooperative, single-threaded execution environment. Unlike modern operating systems that rely on asynchronous, interrupt-driven hot-plug architectures, UEFI relies on its event and timer services along with system management interrupts (SMI) or targeted bus scans to detect newly introduced devices, allocate necessary system resources, and update the global handle database before transferring control to the OS loader.

The Execution Model and Architectural Constraints

The UEFI pre-boot environment operates under a single-threaded, non-preemptive cooperative model governed by Task Priority Levels (TPL). Because the firmware lacks a preemptive scheduler and native asynchronous interrupt infrastructure for general drivers, it cannot handle hot-plug events via standard OS-style hardware interrupts.

Instead, the core framework relies on the EFI_EVENT system and periodic timer callbacks (EVT_TIMER) managed by the DXE (Driver Execution Environment) core. When hardware is plugged into a bus during the pre-boot phase, the event is either buffered by hardware controllers or caught by system firmware operating behind the scenes.

Detection Mechanisms Across Bus Types

Different peripheral architectures utilize distinct mechanisms to discover hot-plug events within UEFI:

1. USB and External Peripherals

USB is the most common pre-boot hot-plug scenario, typically used for keyboards, mice, and installation drives.

  • The host controller driver (such as XhciDxe or EhciDxe) registers an asynchronous timer event with the UEFI core.
  • At fixed intervals, the timer fires at TPL_CALLBACK or TPL_NOTIFY, invoking the controller driver to poll the status change registers (e.g., the Port Status and Control registers).
  • Upon detecting a connection change, the controller driver initializes the port, issues bus resets, assigns an address to the device, and queries descriptors.

2. PCI Express (PCIe) Hot-Plug

Native PCIe hot-plug before OS handoff is more complex due to memory-mapped I/O (MMIO) and bus number constraints.

  • In enterprise servers, physical hot-plug controllers trigger a System Management Interrupt (SMI) handled by the System Management Mode (SMM) firmware.
  • In standard client platforms, hot-plug support is often managed via pre-allocated resources defined in the PCI Bus driver. If a slot supports hot-plug, the platform firmware must pre-allocate bus numbers, I/O ranges, and MMIO space during the initial PCI enumeration pass.
  • If a PCIe device is attached before the boot target is executed, the PciBusDxe driver must be signaled to re-enumerate the downstream bridge and bind device-specific drivers.

Resource Allocation and Driver Binding

Once a new device is physically detected and its basic descriptors are parsed, UEFI integrates the hardware into its active environment:

  1. Handle Database Expansion: The bus driver creates a new handle in the UEFI Handle Database representing the new hardware component.
  2. Protocol Installation: The bus driver installs fundamental identification protocols on the handle, such as EFI_DEVICE_PATH_PROTOCOL and bus-specific protocols (e.g., EFI_PCI_IO_PROTOCOL or EFI_USB_IO_PROTOCOL).
  3. Connecting Drivers via Driver Binding Protocol: The UEFI core's ConnectController() service evaluates registered drivers using the EFI_DRIVER_BINDING_PROTOCOL. Drivers that declare support for the device's hardware signatures (such as EFI_BLOCK_IO_PROTOCOL for mass storage or EFI_SIMPLE_TEXT_INPUT_PROTOCOL for keyboards) are bound to the new handle.
  4. Dynamic Resource Assignment: If the device requires memory or I/O resources, the platform’s resource management protocols allocate space from the pre-reserved pools configured during early chipset initialization.

Transition to the Operating System

Any dynamic hot-plug state changes made during the pre-boot phase must be cleanly communicated or handed off to the operating system:

  • ACPI Table Adjustments: If devices affect global system topology (such as PCIe hot-add in enterprise systems), the platform updates relevant ACPI tables or relies on ACPI DSDT/SSDT control methods (like _HPX for hot-plug parameter extensions and _OSC for operating system capabilities negotiation) to report current hardware status.
  • ExitBootServices Terminations: When the bootloader issues gBS->ExitBootServices(), all periodic timer events, driver polling routines, and UEFI bus drivers are terminated. From this point forward, the operating system's native kernel drivers assume control of the host controllers, clearing pre-boot firmware event buffers and enabling true interrupt-driven hot-plug detection.
