Porting EDK II to Non-x86: Key UEFI Challenges

Porting the open-source TianoCore EDK II framework to non-x86 platforms—such as ARM, RISC-V, or LoongArch—requires bridging foundational hardware and firmware differences. While the Unified Extensible Firmware Interface (UEFI) specification is technically processor-agnostic, the reference implementation in EDK II historically evolved alongside x86 architecture. Consequently, firmware developers encounter substantial hurdles involving CPU execution privilege levels, hardware discovery mechanisms, memory management, toolchain idiosyncrasies, and deep-seated x86 design assumptions.

CPU Privilege Models and Reset Vector Management

x86 platforms boot through standard execution modes (Real Mode to Protected Mode to Long Mode) and follow a well-defined reset vector flow into the Security (SEC) and Pre-EFI Initialization (PEI) phases. Non-x86 platforms manage privilege and boot stages differently:

  • ARM: Execution transitions through Exception Levels (EL3 for Secure Monitor, EL2 for Hypervisor, EL1 for OS/Firmware). Developers must coordinate EDK II execution with ARM Trusted Firmware (TF-A), deciding whether UEFI runs at EL2 or EL1, and properly handing off execution without violating secure execution boundaries.
  • RISC-V: Systems implement Machine (M-mode), Supervisor (S-mode), and User (U-mode). EDK II typically executes in S-mode, requiring integration with an OpenSBI (Supervisor Binary Interface) runtime to handle low-level M-mode operations, I/O access, and timer interrupts.

Porting requires rewriting or implementing platform-specific SEC phase assembly routines to correctly configure early stack pointers, establish exception vectors, and initialize fundamental registers before C-code execution starts.

Memory Management and Cache Coherency

x86 features a strongly ordered memory model and hardware-managed cache snooping, which masks many synchronization bugs. Many non-x86 architectures, particularly ARM and RISC-V, employ weakly ordered memory models:

  • Cache Maintenance: Developers must explicitly flush, invalidate, and clean instruction and data caches during firmware execution, especially when transitioning between boot phases or loading external binaries.
  • Early MMU Setup: Unlike x86, which can run with flat physical memory addressing well into initialization, non-x86 architectures require early Memory Management Unit (MMU) configuration and translation table setup to enforce device memory attributes (e.g., non-cacheable MMIO vs. cacheable Normal memory). Incorrect attribute mapping can lead to silent data corruption, alignment faults, or immediate CPU lockups.

Hardware Discovery: ACPI vs. Flattened Device Tree

UEFI is architected around ACPI tables for platform configuration and standard PCI-based device discovery. While x86 systems feature standard discovery paths, embedded and non-x86 SoC environments differ significantly:

  • Lack of Standard Buses: Many ARM and RISC-V processors use memory-mapped system-on-chip (SoC) fabrics without standardized plug-and-play identification.
  • Device Tree (FDT) Dependency: Embedded ecosystems rely heavily on Flattened Device Trees. Porting teams must choose between writing complete ACPI tables to satisfy standard UEFI expectations or integrating FDT parsing into EDK II drivers to dynamically pass hardware layout information to operating systems.

Interrupt Architecture and Core Timers

EDK II drivers rely on architectural protocols for timers and interrupt controllers (such as the legacy 8259, APIC, and HPET on x86). On alternative platforms, developers must write or adapt drivers for completely different interrupt controller topologies:

  • ARM platforms require implementing the Generic Interrupt Controller (GICv2, GICv3, or GICv4) and programming the ARM Generic Timer.
  • RISC-V systems rely on the Core Local Interruptor (CLINT) or Platform-Level Interrupt Controller (PLIC) alongside SBI timer extensions.

Mismatches in interrupt priority schemes, trigger types (edge vs. level), and core timer frequency discovery frequently cause stalls in the Driver Execution Environment (DXE) dispatcher.

Toolchain and Binary Format Translations

EDK II uses PE/COFF (Portable Executable) binary formats for all driver (PEIM, DXE) and application images.

  • Non-x86 compilers (such as GCC and Clang targeting ARM or RISC-V) natively output ELF binaries.
  • The EDK II build system must cross-compile to ELF and invoke conversion utilities (like GenFw) to transform ELF objects into PE/COFF images.
  • Relocation types specific to non-x86 architectures (e.g., complex jump/call relocations or thread-local storage models) occasionally fail during translation, requiring custom compiler flags (such as -fpie, -fno-jump-tables) and manual linker script adjustments.

Decoupling Legacy x86 Assumptions

Decades of firmware evolution have left x86-specific idioms throughout common EDK II packages. Porting teams routinely need to refactor codebase sections that inadvertently rely on:

  • Port I/O instructions (in/out) rather than memory-mapped I/O (MMIO).
  • x86 System Management Mode (SMM) paradigms, which must be remapped to ARM TrustZone or RISC-V secure enclaves.
  • Assumptions regarding standard PC architecture components, such as legacy real-time clocks (RTCs), standard UART registers, and fixed I/O address ranges.
