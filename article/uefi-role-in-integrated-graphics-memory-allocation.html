UEFI Role in Integrated Graphics Memory Allocation

Unified Extensible Firmware Interface (UEFI) platform policies serve as the foundational governance layer that manages how system memory is apportioned to an integrated graphics processor (iGPU). Because an iGPU lacks dedicated VRAM, it relies on shared system RAM. UEFI platform policies dictate the initial static memory allocations during the pre-boot phase, define upper boundaries for dynamic memory sharing, and establish hardware-level parameters that ensure the operating system and graphics drivers can access video memory without conflicts.

Pre-Boot Initialization and Stolen Memory

During the early boot phases—specifically the Pre-EFI Initialization (PEI) and Driver Execution Environment (DXE) phases—the system memory map is established. UEFI platform policies execute silicon-specific reference code (such as Intel Silicon Reference Code or AMD AGESA) to reserve a dedicated block of system RAM, traditionally referred to as "stolen memory" or the UMA (Unified Memory Architecture) frame buffer.

This static allocation is critical because the display engine requires an active frame buffer to render video before the operating system or dedicated graphics drivers are loaded. The UEFI platform policy programs the integrated memory controller and system address decoders to lock this physical region, rendering it completely invisible to the operating system's general memory manager to prevent memory corruption.

DVMT and Dynamic Allocation Thresholds

Modern architectures balance static reservations with dynamic allocations, such as Intel's Dynamic Video Memory Technology (DVMT). UEFI platform policies define both the baseline floor and the structural ceiling of this architecture:

  • Pre-Allocated Memory (Floor): Platform policies enforce the minimum amount of RAM (commonly between 32 MB and 512 MB) guaranteed solely for graphics initialization, display pipes, and basic hardware management.
  • Maximum Dynamic Memory (Ceiling): Policies define the maximum system memory that the graphics driver can request on-demand from the OS during graphics-intensive workloads.

By defining these boundaries, UEFI ensures that integrated graphics do not starve operating system processes of critical system memory while still scaling performance dynamically during heavy graphics tasks.

Firmware Menus and OEM Customization

Original Equipment Manufacturers (OEMs) use UEFI platform policies to tailor hardware behavior according to a device's form factor, power budget, and thermal limits. In desktop motherboards, UEFI policies are often exposed to users through setup menus under labels such as "UMA Frame Buffer Size" or "DVMT Pre-Allocated."

In mobile, embedded, or thin-and-light devices, OEMs lock these settings via platform policy tables to ensure optimal performance, thermal compliance, and memory efficiency based on the fixed physical memory installed on the board.

Data Handoff via HOBs and ACPI

For the operating system to interact cleanly with integrated graphics, it must understand the memory partitions established before boot. UEFI platform policies record memory configurations into Hand-Off Blocks (HOBs) and translate them into ACPI (Advanced Configuration and Power Interface) tables.

When the OS boots, graphics drivers parse these tables to locate the Graphics Translation Table (GTT), aperture base addresses, and reserved memory ranges. This handoff, orchestrated by the platform policy, guarantees that both the host CPU and the integrated GPU operate with memory coherency and without address overlap.
